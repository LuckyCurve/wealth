# 0004. 压测 = 全局视图叠加（不是独立页面）

## 状态

已采纳（2026-10-30）

## 上下文

需求原话：「对我的资产进行压测，根据分类来，比如分类1下降了 50%，分类2下降了 10%，
我要看看最终表现究竟如何，比如还可以继续多少年的消费，以及消费覆盖率等等，**都跟这变**」。

这句话里最重的是最后四个字。账本上「跟着变」的读数有十几处（报头净资产、目标进度、
月/年/日收益两口径、覆盖标尺与盈余缺口、还需本金外推、加权平均利率、三张旭日图、
消费趋势的「能撑多久」）。这决定了功能的基本形状：它不是**一个新页面**，而是**一层全局滤镜**。

## 决定

### 1. 全局视图叠加，而不是一个「压测页」

压测生效时，页面上所有**从资产金额派生出来的读数**都按打折后的数算；账本本身不动。

理由：做成独立页面就得在页内重复那十几个读数（两套渲染路径必然漂移，且用户要来回对照
「压测前」与「压测后」两页才能判断）。而独立页还有一个更糟的结局：用户会以为压测页
的数字是另一本账。

代价：所有派生读数必须收敛到**一个入口**（`assetsInView()`）。这是这个决定最贵的地方，
也是它唯一的技术风险——散到十几处就必然漂移，症状是同一页上「压测后的覆盖率」
配着「压测前的月收益」。所以它由 `ui-wiring` 契约测试逐处点名把守。

### 2. 账本、快照、导出永远不动

`state.assets[].amount` 是账本事实。压测只在读的时候派生一份打折的副本：
资产列表的金额列、行内金额编辑、快照保存、导出、示例数据全部读原值。

这条不是为了实现方便，是因为**压测是一次假设**。让假设流进账本，一次「点开金额
随手改个尾数」就会把 -50% 写进真实记录。

### 3. 单维度，不跨维度叠加

情景只记**一个**维度（如「资产类型」）下各标签的跌幅。理由：每笔资产在**每个分类**下
都恰好带一个标签，所以「资产类型」与「风险等级」各给一个跌幅时，同一笔钱会被乘两次
（-50% 与 -10% 变成 -55%），而用户完全预期不到那个数。

单维度正好把「分类1 跌 50%、分类2 跌 10%」落成「股票 -50%、债券 -10%」。

### 4. 内置「货币类型」维度不参与

汇率已经是一条**真实在变**的通道。把它塞进压测，用户分不清哪一半是假设、哪一半是
今早的行情。要压测汇率该单独立项。

### 5. 未归类资产按 0% 计入，并在条上报出来

静默给它编一个跌幅等于替用户做假设；整页拦住又是用一件小事挡住主功能。
报出来 + 明确口径（「未归类 ¥X 按未打折计入」）就够。

### 6. 只存**剩余比例**，不存任何金额；落盘

情景形如 `{ catId, keeps: [{ tag, keep }] }`，`keep` 是**剩余比例（%）**。

**为什么存剩余而不是跌幅**（这条是改过的：初版存的是跌幅 `pct`）：滑块问用户的是「还剩多少」——
拉满 100% 就是没有亏损（默认值，最常用），拉到 66% 就是跌了 34%。用户的心智是「还剩多少」，
让他先把「剩 66%」换算成「跌 34%」再填一遍，是白付一道算术；而且默认值会是 0（跌幅 0），
那是个「必须先去清零/设值」的起点，而「没亏」应该是一打开就成立的起点。
所以**存储、滑块、条上的数字三者用同一个语义（剩余）**，跌幅只在报头那行小字里取补数
（`stress.stressDropOf`，换算是单一来源）。

旧存档（跌幅语义的 `drops`/`pct`）在 `keepOfEntry` 一处迁移成补数（pct 0 → keep 100）。
金额一律现算——汇率会变、账本会改，存下来的数第二天就是错的。

落盘（而不是像 `coverageMode` 那样只是视图状态）的理由：压测常常要跨天看
（「如果明天跌成这样，我还撑得住吗」），刷新就清零等于每次都要重设。

失效规则（静默、不弹提示）：维度分类被删 / 标签被删 / 跌幅非法 → 剪掉；剪完为空
或全为 0 → 整条作废（`stress: null`）。「条回到未启用」本身就是可见的交代，
每次开页面弹一次提示只会变成噪声。

### 7. 收益同比例缩

利率是**收益率**不是金额，所以本金缩了收益在 `calcAssetIncome` 里自然跟着缩——
不另写一套打折。覆盖率、还需本金外推都因此自动跟随。

### 8. 指示器两处，同一个「生效」判据

- 资产侧 Tab 栏**之上**的条（横贯全部 5 个资产 Tab）：切到收益测算/资产分布时也要
  看得见「现在读的是打折的数」——只放报头旁就会在那几页失联。
- 页头印徽：压测是**全局**状态，消费模式下也有读数跟着变（读数卡），所以指示器必须
  跟着全局走，不能挂在某个读数上。

## 备选方案与为什么否掉

| 方案 | 为什么否 |
| --- | --- |
| 独立「压测」Tab | 十几个读数要写两遍（漂移），用户还得对照两页；且容易被当成「另一本账」 |
| 允许跨维度叠加（乘法） | 同一笔钱被打两次折，-50% 与 -10% 变成 -55%，用户预期不到 |
| 命中多分类时取最大跌幅 | 语义是「最坏的那个分类」，与「两个事同时发生」不是一回事，且更难解释 |
| 列表金额列也显示打折值 | 压测会通过行内编辑写进账本（最危险的一种） |
| 历史净值也按压测重算 | 那时你并没有这些资产；回填等于篡改历史（与「资产侧校验不碰快照」同一条） |
| 不落盘（每次刷新清零） | 压测常要跨天看，每次重设一遍 |
| 剩余比例允许 >100%（看涨） | 叫「压测」就只做悲观情景；能看涨的东西最后会被当成预测工具，而这页的立场是不预测 |
| 未归类按该维度最大跌幅打折 | 替用户编假设，且降幅会莫名其妙 |
| 把汇率（货币类型）也做成一个压测维度 | 汇率是真实通道，混进来分不清假设与事实 |

## 后果

- 所有派生读数必须经 `assetsInView()`；新增一处派生读数时**先想它该不该跟压测**，
  该跟就走这个入口。`ui-wiring` 逐函数点名把守，`confirmSnapshot` 另有一条**反向**断言
  （它必须读原值，且不得经 `totalAssetsCNY()` 间接叠加）。
- 标签改名要迁移情景里的引用（`migrateStressTagRefs`），分类删除要让情景失效
  （`pruneStress`）——与读数卡所选标签同一处置。
- `index.html` 体积预算抬到 423,000（理由写在 `test/size-budget.test.js` 里）。
