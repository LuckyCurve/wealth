# 界面语言用中文原文作词条键，默认英文

决定：界面文案有两条通道——静态文案挂 `data-i18n`（属性同理挂 `data-i18n-<attr>`），
动态文案在模板里调 `i18n.t('中文原文')`。词条表只有一张英文表（`logic.js` 的 `I18N_EN`），
键就是中文原文；语言是用户设置 `state.lang`（`'en' | 'zh'`），默认 `'en'`，随存档落盘。
缺词条时回落中文原文，不抛错、不显示键名。

为什么键用中文原文，而不是 `settings.theme.title` 这类键名，也不是英文原文：

- **不造第二套命名**。键名要求先想一个词，再在 HTML 里写一遍、在表里再写一遍——三处同名同义，
  改文案要三处对齐；中文原文就是页面上那句话，grep 一下就能找到「这句在哪儿、有没有译」。
- **中文是作者的原话**（账本语气、古纸腔调都在里面）。让英文做源文，等于把中文重打一遍，
  语气会在第一轮翻译里丢掉，之后再也要不回来。
- **默认英文由表提供，而不是由源文案提供**：源文案留在原地，英文缺一句就回落中文——
  漏译是一眼中英混排，不是空白，也不是键名。反过来（英文做源、中文做表）在默认英文下
  永远看不出漏译，只有切到中文才发现。

代价（写在这里是因为它们看起来像 bug，其实是选择）：

- **键是会被改的文案**，改中文原文必须同步改 `I18N_EN` 的键；两条契约测试把守：
  用到的键必须有词条、表里不能有死词条（动态键显式白名单）。
- **`data-i18n` 的属性值与可见文本重复一遍**，于是「这句文案在 HTML 里出现几次」这类计数断言
  会从 1 变 2。断言写到可见文本（`>文本<`）上，别数裸字符串。
- **配置对象里不能直接写 `i18n.t(...)`**：模块级对象在脚本加载时就求值，会把默认语言（英文）
  冻进去，切中文后这些文案不动。文案一律存成取值函数（`() => i18n.t('…')`）。

被否掉的路线：

- **英文原文作键**：默认英文下漏译没有症状（可见），只有中文用户撞上；且中文文案要重打。
- **`settings.theme.title` 式键名**：单文件 SPA 里多一层间接，grep 文案找不回源头。
- **运行时扫 DOM 文本自动翻译**：插值句（「已删除「X」」）只能靠模式匹配，一处对不上就整块漏翻，
  且 MutationObserver 与每次渲染打架。
